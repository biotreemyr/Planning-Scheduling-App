# BTP Planning & Scheduling app: security and workflow review (17/10/2026)

App: BTP Planning & Scheduling (scheduler.biotreegroup.com.my), v1.7.0. A BTB app built on the
same base will follow; most findings apply to it too.

How it was tested: nothing was keyed into live. The live site was probed only as a signed-out
visitor; the code was read; the workflow was walked on a private copy of the live database
(revision 298), which was then deleted. Live stayed at revision 298.

**Security rating: 6.5 / 10.** Fixing S1, S2, S3, S4 and S5 brings it to about 8.5 / 10.

Status column: open until fixed; record the PR when done.

## Security findings

| # | Severity | Finding | Evidence | Fix | Status |
|---|---|---|---|---|---|
| S1 | High | Testing/release results can be forged. A job order change counts as testing or release only when it touches nothing but those fields; mixed changes need only Orders edit. Adding a job order needs only Orders create, whatever fields it carries (tested, released, batch, formula). | `src/lib/auth/workspaceAccess.ts` job order loop (`only(keys, …)` chain, `else need(can.editOrders)`); `jobs.added` needs only `createOrders` | Check each key group separately: any testing key → `passTesting`; any release/reject/poReleases key → `release`; formula keys → `release`; batch keys → `produce`/`editPlan`; remaining keys → `editOrders`. On add, refuse (or require the matching right for) any testing, release, batch or formula field that is set. | Fixed in PR #33 |
| S2 | High | Production results can be forged by planners: a line change that mixes result keys with a date/plan change needs only `editPlan`; an added line needs only `createPlan` even if it carries results. | `workspaceAccess.ts` lines loop (`only(changedKeys(old, line), [...result keys])` else `editPlan`) | Same per-group check: any result key changed or set (completedAt, yieldQuantity, yieldUom, weighed*, actualUnit*, shellWeightMg, startedAt, productionNotes, progress*) → `produce`. | Fixed in PR #33 |
| S3 | High (while running) | The saved `scheduler-local` preview (`.claude/launch.json`) runs `next dev` in demo mode on all interfaces, port 3004, against the LIVE database: anyone on the office network could read and save live data with every permission while it runs. The local guards trust the Host header. | `.claude/launch.json`; `src/lib/persistence/access.ts`; `src/app/page.tsx` (write token handed out in demo) | Add `-H 127.0.0.1` to every dev/preview command, point previews only at a scratch database, and check the socket's remote address, not just the Host header. | Fixed in PR #33 |
| S4 | Medium | The live app listens on all interfaces (`*:3003`): reachable on the office network over plain HTTP, bypassing Cloudflare TLS (sign-in still applies). Other Bio Tree apps bind to localhost. | `lsof` shows `node *:3003`; PM2 `bio-tree-scheduler` runs `npm start` = `next start --port 3003` | `next start -H 127.0.0.1 --port 3003` (package.json `start`), then `pm2 restart bio-tree-scheduler`. | Reopened 18/10/2026: binding `next start` to 127.0.0.1 broke signed-in pages (Clerk rewrite to localhost), reverted in v1.8.1. Block :3003 from the LAN with the macOS firewall instead |
| S5 | Medium | Confirmed machine bookings can be deleted, or their machine/time changed, without Approve or Cancel rights (only a status change to Confirmed/Cancelled is checked). | `workspaceAccess.ts` entries block | Removing a non-Draft booking → `cancel`; changing a Confirmed booking → `approve`. | Fixed in PR #34 |
| S6 | Medium | "Who did it" fields on records are typed by the browser (createdBy, testedBy, releasedBy, rejectedBy, formulaConfirmedBy, batchNumberBy, updatedBy, changedBy). The audit trail uses the real actor, but the record can show a forged name. | `src/lib/domain/workspace.ts` schema; `repository.ts` audit actor | On save, stamp `*By`/`*At` of changed groups from the server actor (or reject values that are not the actor's name). | Fixed in PR #34 |
| S7 | Medium | View-only users receive the whole workspace (all POs, customers, yields) in the page payload; filtering and print rights are enforced only on screen. | `src/app/page.tsx` sends full snapshot; `SchedulerDemo.tsx` hides by capability | Strip sections a user cannot view on the server before sending; re-merge on save (or split the snapshot). | Open |
| S8 | Medium | No security headers on the live site (no CSP, HSTS, X-Frame-Options/frame-ancestors, nosniff, Referrer-Policy); `X-Powered-By` is sent. | `next.config.ts` has no `headers()`; live `curl -I` shows none | Add `headers()` with CSP (frame-ancestors 'none'; script-src self + Clerk), HSTS, nosniff, Referrer-Policy, and `poweredByHeader: false`. | Fixed in PR #34 (check Core sign-in after deploy) |
| S9 | Medium | Database roles are not least-privilege: the scheduler and its "read-only" Core lookups both connect as `biotree` with trust auth (likely owner/superuser). Master Data correctly uses `scheduler_md_reader`. | `.env` DATABASE_URL / BIO_TREE_CORE_DATABASE_URL | Create `scheduler_core_reader` (SELECT only on Core's identity tables) and a non-owner app role; use password/scram auth. | Open |
| S10 | Low | `npm audit`: 5 high, 5 moderate (dompurify via @toast-ui/calendar, uuid via exceljs, sharp/source-map-js via next, prisma/deepmerge-ts via drizzle's optional peer). | `npm audit --omit=dev` | `npm audit fix` where non-breaking; watch for a Toast UI update. | Partly fixed in PR #34: sharp, source-map-js. Left: deepmerge-ts (Prisma, unused), dompurify (Toast UI), uuid (exceljs, breaking) |
| S11 | Low | `.env.backup-2026-10-03` is world-readable (644) and holds an old `sk_test_` Clerk key and a DB URL (git-ignored). | `ls -l .env.backup-2026-10-03` | Delete it (or `chmod 600`) and rotate the test key. | chmod 600 done 17/10/2026; rotate the old sk_test_ key, then delete the file |
| S12 | Low | No rate limit; each save runs heavy validation on up to 8 MB and queries Master Data and Core. | `src/app/api/workspace/route.ts`, `parseWorkspace` | Cap array lengths in the schema; nginx `limit_req` on `/api/`. | App part fixed in PR #34 (20,000-record cap, linear checks); nginx limit_req open |

Done well (keep): verified Clerk session plus fresh Core lookups that fail closed; every save
authorized server-side against the stored snapshot inside the transaction; strict Origin check
against the configured app URL; parameterized SQL; strict zod validation with an 8 MB streamed
limit; no `dangerouslySetInnerHTML` and escaped calendar templates; Excel cells are values, not
formulas; demo mode refused in production builds; `.env` and backups readable only by the owner;
audit rows take the actor from the server.

## Workflow findings (process engineering)

Walked PO PWL005114 (NAC 600 mg capsules, 6 job orders; JO-00002 fully produced and awaiting
testing, JO-00003 part-planned).

| # | Impact | Finding | Suggestion | Status |
|---|---|---|---|---|
| W1 | High | The over-release check ignores job orders whose batch quantity unit differs from the PO's. The PO is in boxes and batch quantity in capsules, so the job order section reads "0 of 2,000 boxes in job orders · 2,000 still to release" while 6 job orders total 2,010 boxes (over the PO) and nothing stopped it. | Compare job orders with the PO in the PO's unit (total packs / boxes), or convert before comparing; block or warn above the PO. | Fixed in PR #34 |
| W2 | High | No QA yield limits are set for this product, so 84.6% final yield and 92% capsulation show neutral, would pass testing unflagged, and no deviation was raised. | Set yield limits per product (or defaults) and show final yield in the Testing list. | Final yield shown in Testing/Release in PR #34; QA to set limits (per product: open) |
| W3 | Medium | Late activities are invisible: JO-00003 Dispensing/Blending/Capsulation planned 28–29/09/2026 are still open, with no late warning, and the Progress grid shows them like any planned cell. | Amber/red "late" colour in the Progress grid and plan, plus a warning for open activities past their date. | Fixed in PR #34 |
| W4 | Medium | WIP handovers are never acknowledged: all four of JO-00002's handovers are still "not received" yet each next process completed, so who took over the material is not recorded. | Require receipt before the next process can start (or remove the receipt step). | Fixed in PR #34 (receipt required) |
| W5 | Medium | Double booking not flagged: machine `db-01` is booked 28/09/2026 08:00–17:00 for JO-00002 (completed) and JO-00003 (draft); the board shows 0 conflicts because completed bookings are skipped. | Include completed bookings when checking an open booking for clashes. | Fixed in PR #34 |
| W6 | Medium | Route set-up needs a process-engineering review: Blending is required for every dosage form (including sachets) and comes before Granulation; usually the final blend/lubrication follows granulation and not every product is blended. | Confirm the order in Admin → Units; consider Blending optional or limited to the forms that use it. | Decided 17/10/2026: Blending required, once, before or after Granulation (optional). Fixed in PR #34 |
| W7 | Low | The capsule batch quantity offers "boxes" and "sachets" as units. | Limit the unit to the dosage form's (tablets or capsules). | Fixed in PR #34 |
| W8 | Low | Planned dispensing 6 × 43.5 kg = 261 kg against an order total of 259.2 kg, with no overage shown. | Show overage %, warn above a set limit. | Fixed in PR #34 (overage shown, warns above 1%) |
| W9 | Low | Reports show "Updated … 10/16/2026" (month first); everything else is DD/MM/YYYY. | Format every date DD/MM/YYYY (rule now in bio-tree-ui-ux-handoff.md). | Fixed in PR #34 |

Suggested order of fixes: S1, S2 (forgery of GMP records), then S3, S4 (one-line binds), W1, W3,
W9, then S5, S6, S8, W4, W5, then the rest.
